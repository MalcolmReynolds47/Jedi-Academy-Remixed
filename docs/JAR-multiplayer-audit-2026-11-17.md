# JA:R audit — November 17, 2026

**Follow-up, November 20:** The seven findings below describe 1.340.0. See the
[1.341.0 changes](../CHANGELOG.md) for their fixes and the manual ZIP expansion step.

**Release decision:** Keep 1.340.0 staged. It contains the fix for the reported crowd Undo crash and passed the configured suite. Two defects reproduced outside that suite: cleanup can delete the useful rollback backup, and NPC squad sorting loses information. The native world smoke also fails before several other checks can run. Fix rollback first, then squad sorting. No runtime files or installation were changed by this audit.

The review covers multiplayer and the shared code, content, and release tooling it uses. It combines inspection of the current tree, isolated runs of the packaged native server, the configured Release CTest suite, and a review of earlier gameplay evidence. It is not a line-by-line certification, a new SP campaign playthrough, or an Internet multiplayer playtest. [Machine-readable evidence](audits/2026-11-17-evidence.json) preserves the measurements independently of build-directory cleanup.

| Priority | Finding and consequence | Recommended fix and acceptance check |
| --- | --- | --- |
| 1 | **Cleanup can destroy the rollback from the last actual install.** The deployer records a successful reinstall even when zero files changed; retention keeps only the newest matching deployment's backup. In a disposable build tree, a one-file deployment followed by a zero-change receipt caused the real retention function to delete the prior backup and leave both receipts. This did not touch the Steam backups. [Retention](../scripts/jar-build-retention.ps1#L14) · [receipt writer](../scripts/deploy-jar-release.ps1#L235) | Retain the most recent rollback-bearing transaction for the installed target across no-op deployments. Test install A → B → reinstall B → prune → restore A; compare restored hashes. Test two installation roots independently. |
| 2 | **Squads measure the enemy's distance from itself.** The same enemy entity is passed to both waypoint lookups. A compiled test of the actual sorter gave three differently positioned members costs of `0, 0, 0`. A second defect is masked by the first: the loop meant to shift an occupied row never runs. Supplying costs `30, 20, 10` retained only the third member and two empty sentinels. This is independent of the crash fixed in 1.340.0; no new crash is claimed. [Waypoint lookup](../codemp/game/NPC_AI_Utils.c#L146) · [insertion loop](../codemp/game/NPC_AI_Utils.c#L176) | Fix the member lookup and the ordering together. Verify that every original member survives exactly once for ascending, descending, equal and unreachable costs. Then repeat the staged crowd/Undo and ranged-combat tests. |
| 3 | **One legacy rope fixture blocks the broader native world tests.** On retail `mp/ffa3`, its crate and NPC each loaded, the unlinked pair loaded, and the crate-to-world rope loaded. Adding only the crate-to-NPC link between the two distant spawn points rolled back the whole load. The smoke constructs length from straight-line distance plus 100, without establishing a feasible route. On Flatgrass the same two object types 128 units apart on a 192-unit rope loaded, saved in the current format, cleared and reloaded with both objects and their link. The failure is real; it does not establish that ordinary linked saves are broken, or identify the exact routing rejection. [Fixture](../scripts/mp_world_smoke.py#L288) · [test ordering](../scripts/test-mp-server.py#L310) · [runtime rollback](../codemp/game/g_jar_duplicate.inc#L453) | Give the happy path known clear geometry; keep the failing long route as a separate negative case and report the reason for rejecting it. Run autosave, joints, attachments, and rigid-body checks independently, so one setup assertion cannot suppress them. Test a previously valid real-world save before promising backwards compatibility. |
| 4 | **Old visibility tests accumulate nested game folders.** Retention removes some named top-level outputs but misses these older fixtures. Together two folders list 40.95 GB of file paths, including 248 PK3 entries. Accounting by file identity yields 3.02 GB of distinct file content; 1.79 GB has all its directory links inside the pair. Neither number is a measurement of allocated space that deletion would free. [Cleanup rules](../scripts/jar-build-retention.ps1#L39) | Have each run identify its temporary runtime trees separately from evidence to keep. Dry-run cleanup using unique file IDs. Verify the stage, Steam rollback, separately requested friend archives, results and crash stacks survive. Nothing was deleted from these old folders. |
| 5 | **Host-map search can hide a map whose display title has not been read yet.** Maps without arena titles rely on lazy BSP inspection. Search filters on known titles and filenames, but inspection runs only on visible filtered rows. An off-page map whose title alone matches never reaches inspection. This is a source observation; graphical typing was not tested. [Filtering](../codemp/ui/ui_jar_host_maps.inc#L115) · [refresh](../codemp/ui/ui_jar_host_maps.inc#L186) | Index titles independently of the filtered rows while keeping previews lazy. Open a catalog with more than one page and search immediately by a title absent from its filename and arena metadata; repeat after reopening. |
| 6 | **The full distribution stores most MP appearance assets twice.** 1,766 of 1,767 members of MP `jar-interface.pk3` matched the same path and uncompressed SHA-256 in SP `jar-appearance.pk3`. The matching MP entries alone account for 640,791,110 compressed member bytes. This is an opportunity, not a promised ZIP reduction. | Measure a distribution prototype that materializes the required private archives at install time. Compare final hashes and test a pure server. Do not mount the assets in the stock base folder, silently change the protocol or archive checksums, or replace the separately requested friend ZIP. |
| 7 | **Player documentation misidentifies the installed release.** The multiplayer guide's first “Latest installed release” heading names 1.94.0, although the local verified installation is 1.339.0. [Player guide](JAR-multiplayer.md#latest-installed-release-1940-2026-11-12) | Label old entries as history. Provide one current release pointer, and distinguish staged, installed on this machine, and distributed to a friend. |

## What was checked

| Area | Evidence and its limits |
| --- | --- |
| Release identity, launcher, deployment | Verified the full 1.340.0 ZIP (build `20261116-211610-7177d4c9`) with the project verifier and checked the installed 1.339.0 files against the deployment receipt. The configured launcher and install-path tests passed. Rollback was exercised only in a disposable tree; no install, rollback, or owner launcher invocation took place. |
| Hosting, networking and maps | Pure staged dedicated server, protocol 1051, two independent local UDP clients: compressed connection, native game state, active snapshots, valid proof acceptance and invalid proof rejection. Both `gm_construct` and `gm_flatgrass` separately loaded and served the two clients. Portal state and native gravity/friction changes passed separate network scenarios. The isolated base test ignored deliberate JAPro overrides and still loaded an unrelated custom pack. These runs did not render frames, exercise the owner's router, or establish a remote player's view. |
| NPCs, combat and Undo | In the fresh native NPC scenario, the entity count went `1 → 2 → 1 → 0`, and the observer saw cleanup. Prior packaged evidence for this exact build includes four 70 → 69 Undo cases, and the symbolized crash on 1.339.0. The audit's sorter test is new. Neither a specific NPC aiming choice in live gameplay nor sustained high-crowd frame time was measured by that unit test. |
| Physics, tools, context, ownership and persistence | Configured tests covered model hulls, native joints/rope paths, duplication, Sandbox policy, movement, and context state. Native controls distinguished the legacy load failure from a successful current-format linked save. A fresh graphical check of physgun aim, tool feel and remote-player consent was not performed. |
| Models, sabers, entities and presentation | A fresh native appearance test admitted 26 adapted models and exercised four hilts and custom RGB over UDP. Server executable and game DLL matched the stage by hash. Catalog, weapon resources, face/audio, lightmap/fog, sky, reflection, camera and renderer DLL checks passed in the configured suite. These checks do not establish that every skin renders, every sound is audible, or every spawn card works on every map. |
| Coverage outside this pass | Spawnable map sections remain last in the owner backlog. Individual section playthroughs, all SP campaign paths, a graphical listen host plus a separate physical client, WAN joining, and a long mixed-NPC/physics performance run were not newly qualified. The historical owner feedback is not treated as a new test. |

## Release and next checks

The 1.340.0 ZIP is 1,507,407,826 bytes, SHA-256 `9D093CB3E5BDB53ADB99E66544C13489E1EFAD83DABFBC7B6B37ECAB1B99E0B0`; the verifier reported 75 files. The installed 1.339.0 receipt matched all 75 listed files. Both 1.257.0 multiplayer test ZIPs and the 1.257.0 maps ZIP are still present, separate from the stage. Do not treat those older executables as an independent test of 1.340.0. The configured suite passed **159/159**; the separate world integration failure above is deliberately reported alongside that count.

After the first three fixes, exercise a graphical listen host with a second machine joining mid-fight: compare NPC identity, firing, fall damage, model visibility, local versus remote player permissions, and Undo counts. Run a sustained mixed crowd and record server frame time, memory growth, and client snapshot gaps as the population grows. Those measurements would establish what remains playable; a large successful spawn count alone cannot.
